# ADR-0138：入库整理 MP4 布局，存量播放使用虚拟头

- 状态：已接受
- 日期：2026-11-10
- 关联：[媒体引擎](0002-media-engine-and-stash.md)、[消费者边界](0134-consumer-control-and-privacy.md)

## 问题

普通 MP4 即使索引位于开头，也可能有数千个顶层 `mdat`。部分 HTTP 解析器为跳过这些盒子连续发起 Range 请求，起播耗时由请求往返主导。读取线程优化和硬件解码不能消除这些请求。不得仅凭扩展名或起播零帧判为编码故障。

## 决策

复用现有 MP4 盒子工具、头部拼接响应和入库媒体探测。只识别单个前置 `moov`、没有 `mvex`/`moof`、媒体开始之后只有 `mdat` 和填充盒子的完整文件；读取盒子数量和头大小均有上限。未知、尾部索引、分片与不完整布局不改写。

将首个 `mdat` 的四字节长度设为零，使其延伸到文件末尾。后续 `mdat` 的头成为未被样本表引用的填充；所有样本地址、时间戳、音视频压缩字节与文件大小均不变。这个操作不调用编解码器，也不生成整片缓存。

本地新入库影片在现有媒体属性探测阶段完成原位整理，之后直接复用源文件。写前持久保存原长度、头摘要、文件身份和时间；探测失败回滚，未完成事务在下一次探测时先恢复，文件身份不匹配时拒绝恢复并保留记录。成功写入更新修改时间，使旧文件头和身份缓存失效；回滚恢复原时间。软链接和多硬链接文件不原位处理。恢复记录存于数据根状态目录，大小与影片长度无关。远程来源不自动改写。

已有馆藏播放时，兼容浏览器的编码才进入虚拟头路径：仅在响应中替换相同字段，后续媒体仍读取原片。结果按路径、大小、修改时间缓存，内存最多保留四份文件头。准备好的头沿用既有 `.mp4hdr` 边车持久保存，重启后顺序读取小型边车，不再逐盒跳读原片；资产清理沿用原有边车回收。播放不会启动整片重封装，也不会修改源文件。原有缺失 `ctts` 的修复与转换路径保持独立。

其他封装问题暂不自动重封装。确需 FFmpeg 搬移数据时，必须有临时空间、验证和替换事务；空间不足不能冒险覆盖。新增全片处理路径需要独立验收，不回退到无界的播放时整片复制。

## 验收

合成多 `mdat` 样本逐项核对地址与样本内容；覆盖异常长度、尾部附加盒子、读取上限、原位四字节差异、失败回滚、崩溃恢复和文件替换保护。API 覆盖跨补丁边界的 Range 与 HEAD；入库覆盖本地成功、探测失败和远程不改写。

真实完整样本的私有对照验证压缩流哈希、HTTP 请求数、隔离浏览器首帧与中段跳转；公共记录不包含馆藏路径、影片标识或凭据。这些对照不能代替运行中安装包的升级验收。
